---
title: Several brands
description: List the rows of several brands, tenants or companies in one query with perimeters that read the brand of the row, and decide a parent in the brand of each child row with decidedInRowContext().
---

A decision runs under one [decision context](/essentials/readers#the-decision-context): the one the resolver returns when the decision is made. This page covers the lists that span several brands, companies or tenants in one query. Replace "brand" with the dimension of your application.

## The brand is a value of the row

Do not build such a list by switching the decision context between `controlledFor()` calls joined with `orWhere()`. Only the list would follow each branch: `withAbilities()`, the policy, the kept decisions, `Access::preload()` and the row checks of laravel-rest-api run under the context in force, not under the brand of each row. A post of brand B listed through the rights of brand B would be decided for `update` with the rights of brand A, and kept so.

When one list spans several brands, the brand is a value of the row, not of the request. Write perimeters that read the brand of the row and filter by the brands where the reader holds the right:

```php [app/Access/Controls/PostControl.php]
protected function perimeters(): array
{
    return [
        BrandPerimeter::new()
            ->allowed(fn (User $user, Ability $ability): bool => $user->brandsWhere("{$ability} brand posts") !== [])
            ->should(fn (User $user, Post $post, Ability $ability): bool => in_array($post->brand_id, $user->brandsWhere("{$ability} brand posts"), true))
            ->query(function (Builder $query, User $user, Ability $ability): void {
                $query->whereIn('brand_id', $user->brandsWhere("{$ability} brand posts"));
            }),
        OwnPerimeter::new()
            ->allowed(fn (User $user, Ability $ability): bool => $user->brandsWhere("{$ability} own posts") !== [])
            ->should(fn (User $user, Post $post, Ability $ability): bool => $post->author_id === $user->id && in_array($post->brand_id, $user->brandsWhere("{$ability} own posts"), true))
            ->query(function (Builder $query, User $user, Ability $ability): void {
                $query->whereBelongsTo($user, 'author')->whereIn('brand_id', $user->brandsWhere("{$ability} own posts"));
            }),
    ];
}
```

`brandsWhere()` stands for a method of your application that returns the brands where the user holds a permission. `Post::controlled()` then lists the posts of every brand of the reader in one query, and the policy, `withAbilities()` and `Access::preload()` decide each row from its own brand, whatever the current one.

- **Keep these perimeters out of `Levels::of()`.** A group applies only the highest level the reader reaches, in any brand: a reader who sees every post of brand A and only their own posts of brand B would lose their posts of brand B. Loose perimeters add up, each filtered by its own brands.
- **Keep the brand out of the boundary.** `Boundary::where()` holds one value per reader, so a boundary that reads the current brand cuts the list to that brand. Keep in the boundary what is the same for every row the reader may reach, such as the tenant.
- Check the result with [`assertControlAgrees()`](/testing-and-tooling/testing#the-decisions) on posts of several brands.

### One level per brand

The loose perimeters already give each brand its own level: in each brand, their union is the highest level the reader reaches there. Never wrap a group, or its levels, in a perimeter that picks the level brand by brand: the package reads only what each perimeter of the list declares.

To keep what a group saves, the lower levels left out of the SQL, filter each lower level by the brands where no higher level applies:

```php
OwnPerimeter::new()
    ->allowed(fn (User $user, Ability $ability): bool => $user->brandsOnlyWhere("{$ability} own posts", above: ["{$ability} brand posts"]) !== [])
    ->should(fn (User $user, Post $post, Ability $ability): bool => $post->author_id === $user->id && in_array($post->brand_id, $user->brandsOnlyWhere("{$ability} own posts", above: ["{$ability} brand posts"]), true))
    ->query(function (Builder $query, User $user, Ability $ability): void {
        $query->whereBelongsTo($user, 'author')->whereIn('brand_id', $user->brandsOnlyWhere("{$ability} own posts", above: ["{$ability} brand posts"]));
    }),
```

`brandsOnlyWhere()` stands for `brandsWhere()` of the first permission minus the brands of every higher level, whose permissions `above` lists, so each brand is read by one level only.

### Search keys

On a searchable model, key these perimeters by the brand of the row and the brands where the reader holds the `view` right:

```php
BrandPerimeter::new()
    // allowed(), should() and query() as above
    ->searchKeys(
        name: 'brand',
        row: fn (Post $post) => $post->brand_id,
        reader: fn (User $user) => $user->brandsWhere('view brand posts'),
    ),
OwnPerimeter::new()
    // allowed(), should() and query() as above
    ->searchKeys(
        name: 'own',
        row: fn (Post $post) => [[$post->brand_id, $post->author_id]],
        reader: fn (User $user) => array_map(fn (int $brand): array => [$brand, $user->id], $user->brandsWhere('view own posts')),
    ),
```

The key of an own post holds its brand with its author: an author key alone would find the reader's posts in every brand, even one where they hold no right. `Post::search()->controlled()` finds the posts of every brand of the reader, and laravel-rest-api serves the lists and the searches of several brands under one decision context, with its extension as it is. Check with [`assertSearchAgrees()`](/testing-and-tooling/testing#the-search) on posts of several brands.

## A child read through its parent

A [`ThroughParent`](/essentials/parents) decides its parent under the decision context of the request, and never reads the brand of the child row. With the perimeters above, which read the brand of the row and never the current brand, that changes nothing: a comment is readable wherever its post is. A condition on the comment's own brand and the reader's rights goes in the comment's boundary.

It is different when the control of the parent reads the brands from the decision context, such as `['brands' => '1,2']` for a headquarters that reads two brands. The parent is then decided under the whole context, and being readable in any one of its brands is enough. Take a post P readable only in brand B, and a comment of brand A on P under a comment boundary that keeps the brands of the request: under A and B, the comment is listed and granted, since P is readable in B, though neither brand alone grants it. Every path agrees on this wide answer, so the assertions cannot catch it.

`decidedInRowContext()` decides the parent, for each child row, within the brand that the row holds.

### Declaring the switch

Declare once, in the `boot()` method of a service provider and next to `Access::decisionContextUsing()`, the values that the request covers and how the application acts in one of them. `Brands` stands for the state of your application:

```php [app/Providers/AppServiceProvider.php]
use Closure;
use Lomkit\Access\Access;

public function boot(): void
{
    Access::decisionContextUsing(fn (): array => ['brands' => Brands::requested()->sort()->implode(',')]);

    Access::rowContextUsing(
        values: fn (): array => Brands::requested()->all(),
        within: fn (int|string $brand, Closure $decide): mixed => Brands::actingIn([$brand], $decide),
    );
}
```

```php
public static function actingIn(array $brands, Closure $callback): mixed
{
    $previous = self::$requested;
    self::$requested = $brands;

    try {
        return $callback();
    } finally {
        self::$requested = $previous;
    }
}
```

- `values` returns the values that the request covers, ints or non-empty strings, exactly as stored in the column of the child rows; an empty list reaches nothing. It must read the same state as the decision context.
- `within` switches the application to the single value it receives, every state that the parent reads included (the brands, the team of a permission package, a tenant), calls `$decide` exactly once, and restores the previous state in a `finally` block.
- Keep both cheap: they run once per value for each list, and for the first row check of a reader, ability and context in a request.
- Only the PHP state is switched: `within` runs while the package builds the SQL, and the query runs after it returns. Keep out of the rules of the parent a state that the database reads, such as a session variable or a row-level security policy.

Then name, on the `ThroughParent`, the column of the child row that holds the value:

```php [app/Access/Controls/CommentControl.php]
ThroughParent::belongsTo('post', inverse: 'comments')
    ->decidedInRowContext('brand_id'),
```

### What it changes

The SQL gets one branch per value of the request, each built while `within()` runs for its value:

```sql
where (
     (comments.brand_id = 'A' and exists (select * from posts where posts.id = comments.post_id and (<PostControl within A>)))
  or (comments.brand_id = 'B' and exists (select * from posts where posts.id = comments.post_id and (<PostControl within B>)))
)
```

- A child row whose value is `null`, or not one of `values`, has no branch: the `ThroughParent` refuses it. Reach such rows through another perimeter.
- The policy, the row checks, `withAbilities()`, `Access::preload()` and `reachableKeys()` use the same branches.
- A decision without a row is granted when there is a value of the request in which the `allowed()` of the `ThroughParent` accepts and the parent reaches a perimeter.
- A draft reads the column from its attributes, like the foreign key.
- The decisions on the parent are kept under the context of each value, the same key as a request of that value alone.
- `access:check` prints `row context brand_id` on the line of the `ThroughParent`, and `--json` gives `parent.row_context`.

Each row gets the answer of its own value alone. That narrows the wide answer only when the rules of the parent grow with the brands: each rule that reads the brands filters the rows by them, and each `allowed()` that reads them accepts as soon as the reader holds the right in one of them. A rule that grants more for fewer brands would open, within one value, a parent that the whole request does not open. No assertion checks it.

### Searching through the parent

A searchable child whose `ThroughParent` is `decidedInRowContext('brand_id')` writes the value of the child row after the relation: `through.post.in.1.2.workspace_id.1.author.7` for a comment of brand 1. A child without a value carries no key through that parent. The reader gets, for each value of the request where the `allowed()` of the `ThroughParent` accepts, the keys of the parent computed within that value. See [Searching through a parent](/search/through-a-parent).

### Errors

| Mistake | Exception |
| --- | --- |
| `decidedInRowContext()` without `Access::rowContextUsing()` | `MissingRowContextException`, when the control is built |
| `values` returns something else than a list of ints and non-empty strings | `InvalidRowContextValuesException` |
| `within` does not call `$decide` exactly once, leaves the decision context changed, decides under the context of the whole request or of another value, or switches two values to the same context | `RowContextSwitchException` |
| The column is not a plain column name | `InvalidRowContextColumnException` |
| `decidedInRowContext()` twice on one `ThroughParent` | `DuplicatePerimeterCallbackException` |
| The `ThroughParent` is a level of `Levels::of()` | `RowContextInLevelsException`: declare it next to the group |

### Testing the switch

`assertRowContextAgrees()` compares each row with a request of its value alone, which the test sets up itself through `alone`, without the `within` closure under test:

```php
public function test_the_brand_switch_is_complete(): void
{
    foreach ([$this->headquarters, $this->brandManager] as $reader) {
        $this->assertRowContextAgrees(
            CommentControl::class,
            $reader,
            Comment::uncontrolled()->get(),
            alone: fn (int|string $brand, Closure $check): mixed => $this->asBrandRequest($brand, $check),
        );
    }
}
```

- `alone` receives a value and a callback, sets up every state of a real request of that value alone, calls the callback and restores the state. `asBrandRequest()` stands for that helper of your tests.
- For each row whose value is one of the request, the assertion compares the answer under the request with the answer inside `alone`, through the Gate and through `controlledFor()`, for `view`, `update` and `delete` by default (pass others as `abilities`).
- It catches a `within` that forgets a state the parent reads, and a perimeter or boundary of the child that reads the brands of the request instead of the brand of the row. It does not check that the rules of the parent grow with the brands.
- The control declares exactly one column with `decidedInRowContext()`, and at least one row holds a value of the request.

### Without the switch

Without `decidedInRowContext()`, serve the children of such a parent one brand at a time, with a boundary on the child that keeps its rows to the brand of the request. To show several brands on one page, run one query per brand, switch the decision context between them, and decide everything the page needs on those rows, `withAbilities()`, every `can()` and the API resources that check them, while the context of their brand is in force. Never join those queries with `orWhere()`. laravel-rest-api decides under the context of the request, so there one brand at a time means one brand per request.
