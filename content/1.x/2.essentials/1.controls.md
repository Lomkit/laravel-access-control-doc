## Writing a control

A control is a class that extends `Lomkit\Access\Controls\Control`. It names its model and lists its perimeters:

```php [app/Access/Controls/PostControl.php]
namespace App\Access\Controls;

use App\Access\Perimeters\OwnPerimeter;
use App\Models\Post;
use App\Models\User;
use Illuminate\Database\Eloquent\Builder;
use Lomkit\Access\Ability;
use Lomkit\Access\Controls\Control;

class PostControl extends Control
{
    protected string $model = Post::class;

    protected function perimeters(): array
    {
        return [
            OwnPerimeter::new()
                ->allowed(fn (User $user, Ability $ability) => $user->can("{$ability} own posts"))
                ->query(function (Builder $query, User $user): void {
                    $query->where('author_id', $user->id);
                }),
        ];
    }
}
```

- `$model` is the Eloquent model that the control decides on, declared as the default value of the property. A `$model` that is missing, is not a class or is not an Eloquent model throws `InvalidControlModelException`.
- `perimeters()` lists the [perimeters](/essentials/perimeters): loose perimeters, which add up, and [`Levels::of()`](/essentials/levels) groups.
- `boundary()`, optional, declares a condition that every row must meet, such as the tenant of the user. See [Boundaries](/essentials/boundaries).

The model uses the `HasControl` trait, which adds the [controlled queries](/essentials/queries):

```php [app/Models/Post.php]
use Lomkit\Access\Controls\HasControl;

class Post extends Model
{
    use HasControl;
}
```

## Generating a control

```bash
php artisan make:control PostControl
```

The command writes `app/Access/Controls/PostControl.php`. Its options:

- `--model` (`-m`) names the model: `--model=Post` for `App\Models\Post`, or a fully qualified class such as `--model='Domain\Blog\Post'`. Without it, the model is named after the control, `App\Models\Post` for `PostControl`. The command refuses, and writes nothing, when the model is not an Eloquent model class.
- `--perimeters` (`-p`), repeatable, lists perimeter classes of `app/Access/Perimeters`. The control gets an `allowed()`, `should()` and `query()` callback for each one, which refuse everything until you write them, except the callbacks of the [hooks](/essentials/perimeter-classes#rules-in-the-class) that the class overrides. The perimeters are listed as loose perimeters: group the levels of a hierarchy in `Levels::of()` yourself.
- `--parent`, repeatable, writes a [`ThroughParent`](/essentials/parents) entry for a `belongsTo` relation of the model, such as `--parent=post`.

```bash
php artisan make:control PostControl --model=Post --perimeters=GlobalPerimeter --perimeters=OwnPerimeter
```

## Finding the control of a model

The package links a model to its control in two ways.

### Discovery

The controls in `app/Access/Controls` are discovered: the package reads their `$model`. A model without anything more is linked to the discovered control whose `$model` it is.

Add directories with `Access::discoverControlsIn()`, in the `boot()` method of a service provider:

```php
use Lomkit\Access\Access;

public function boot(): void
{
    Access::discoverControlsIn([app_path('Domain/*/Controls')]);
}
```

- The calls add up: each module can add its own directory from its provider. `app/Access/Controls` is always scanned, and no call removes a directory.
- The paths accept glob patterns. Pass absolute paths (`app_path()`, `base_path()`, `__DIR__`), since a relative path depends on the working directory.
- The same directory given twice is scanned once.

### The `#[ControlledBy]` attribute

A model can name its control itself. A control outside the discovered directories is only found this way:

```php [app/Models/Post.php]
use App\Access\Controls\PostControl;
use Lomkit\Access\Attributes\ControlledBy;
use Lomkit\Access\Controls\HasControl;

#[ControlledBy(PostControl::class)]
class Post extends Model
{
    use HasControl;
}
```

### One control per model

A model has a single control. Two controls for the same model, two discovered controls or a discovered control and the one the attribute names, throw `DuplicateControlException`, which names both, whatever the order. Put the variations, such as what administrators see, in the perimeters of the single control.

A model with neither a discovered control nor the attribute has no control: its controlled queries throw `MissingControlException`, and `Access::registerPolicies()` gives it no policy.

## The Access facade

`Lomkit\Access\Access` reaches the controls:

```php
use Lomkit\Access\Access;

if (Access::hasControl($model)) {
    $control = Access::controlFor($model);
}
```

- `Access::controlFor($model)` returns the control of a model, given as an instance or a class name, or throws `MissingControlException`. `Access::hasControl($model)` checks first.
- `Access::control(PostControl::class)` and `PostControl::new()` return the instance of that control. There is one instance per control class, resolved through the container, so a control can take constructor dependencies.

There is no runtime list of the controls: `#[ControlledBy]` is resolved model by model. Guard with `Access::hasControl()` on the model at hand.

## Pure perimeter lists

A control builds its perimeters and its boundary once, and keeps them for the whole process: a request, a queue worker or an Octane worker that serves many requests. `perimeters()` and `boundary()` must therefore return the same declarations every time. Read the user, the request, the tenant, the configuration of the moment or the clock in the callbacks, which receive the user, never while building the list:

```php
// Wrong: the client of the first user is kept for the whole worker
protected function perimeters(): array
{
    $client = auth()->user()->client_id;

    return [
        ClientPerimeter::new()
            ->allowed(fn (User $user) => $user->client_id !== null)
            ->query(fn (Builder $query) => $query->where('client_id', $client)),
    ];
}

// Right
protected function perimeters(): array
{
    return [
        ClientPerimeter::new()
            ->allowed(fn (User $user) => $user->client_id !== null)
            ->query(fn (Builder $query, User $user) => $query->where('client_id', $user->client_id)),
    ];
}
```

In debug mode and in tests, the package builds the list again each time it hands out a control and throws `ImpurePerimetersException` when the result differs. The check compares the classes, the callbacks and the values they capture: it catches a user, a date or a configuration value read at build time, but not the state hidden inside a service.

## Caching the controls

In production, cache the control of each model:

```bash
php artisan access:cache
```

`php artisan optimize` runs it, and `php artisan access:clear` removes the cache. Run it again in every deployment, after adding, moving or deleting a control.

`php artisan access:check` builds every control and reports what would throw, open or hide rows. See [access:check](/testing-and-tooling/access-check).
