## The three callbacks

A perimeter declares one access rule: which users it applies to, and which rows it reaches.

```php
use App\Access\Perimeters\OwnPerimeter;
use Illuminate\Database\Eloquent\Builder;
use Lomkit\Access\Ability;

OwnPerimeter::new()
    ->allowed(fn (User $user, Ability $ability) => $user->can("{$ability} own posts"))
    ->should(fn (User $user, Post $post) => $post->author_id === $user->id)
    ->query(function (Builder $query, User $user): void {
        $query->where('author_id', $user->id);
    });
```

| Callback | Question | Used by |
| --- | --- | --- |
| `allowed()` | Does the perimeter apply to this user, for this ability? The **permission**. | everything |
| `query()` | Which rows does it reach? Constraints on the query, for the **lists**. | `controlled()`, and the row check when there is no `should()` |
| `should()` | Is this row one of them? The **row check**, in memory. Optional. | the policy, drafts |

Take a user who may only see their own posts. `allowed()` says that they hold the `view own posts` permission. `should()` checks, in the policy, that the post at hand belongs to them. `query()` gives their posts for the lists.

`query()` and `should()` are two rules you write, so they must describe the same rows. `assertControlAgrees()` proves it on your test data, see the Testing and tooling section.

### `allowed()`

```php
->allowed(fn (User $user, Ability $ability) => $user->can("{$ability} client posts"))
```

- It receives the user and the ability. The ability converts to its name in a string: `"{$ability} client posts"` reads `view client posts`, `update client posts`, `approve client posts`.
- It must return a boolean: any other value throws `PerimeterCallbackResultException`.
- It never sees a row. A condition on the row goes in `should()` and `query()`, or in the [boundary](/essentials/boundaries).
- It runs once per user, ability and request, whatever the number of rows, and the policy, the queries and the search share its answer. See [Readers](/essentials/readers#kept-decisions).

### `query()`

```php
->query(function (Builder $query, User $user, Ability $ability): void {
    $query->where('client_id', $user->client_id);
})
```

- It constrains the builder it receives and returns nothing. An arrow function that returns that same builder works too.
- Returning another builder, such as `Post::query()->where(...)`, throws `QueryCallbackReturnedAnotherBuilderException`.
- A callback that adds no `where`, or only orders, limits or skips its constraint under a condition, throws `EmptyQueryCallbackException`. For every row, use [`unrestricted()`](#unrestricted-perimeters). For a user who reaches no row, refuse them in `allowed()`, or add `$query->whereRaw('0=1')`.
- A join throws `JoinInPerimeterException`, since Laravel drops the joins of a nested `where` group. Use `whereHas()` or an `exists` subquery.
- The ability, the third parameter, is optional. The controlled queries pass the ability they list: `view`, unless `controlled('update')` names another one.

### `should()`

```php
->should(fn (User $user, Post $post, Ability $ability) => $post->author_id === $user->id)
```

- It receives the user, the row and, optionally, the ability, and must return a boolean.
- It is optional. Without it, the policy checks a saved row through `query()`, in one SQL query on the row's key. With it, the row is checked in memory, without a query.
- A row about to be created, a **draft**, is not in the database: only `should()` can judge it. Keep `should()` on the perimeters through which users create rows. See [Policies](/essentials/policies#drafts).
- The policy passes the row as it is stored: after `fill()`, `should()` receives the original values. See [Policies](/essentials/policies#decisions-on-the-stored-row).

Drop a `should()` that only repeats its `query()` when no user creates rows through the perimeter: the row is then checked in SQL.

## The ability

Each callback receives a `Lomkit\Access\Ability`, an immutable value object:

```php
use Lomkit\Access\Ability;

Ability::view();           // also create(), update(), delete(), restore(), forceDelete()
Ability::of('approve');    // any business ability
$ability->is('view');      // compare by name, with a string or an Ability
$ability->name();          // 'view'
"{$ability} posts";        // 'view posts'
```

- Type the ability parameter `Ability $ability`. An untyped parameter, or one typed `string`, throws `AbilityParameterTypeException` when the perimeter is declared. `?Ability`, `Stringable`, `object`, `mixed` and unions that contain `Ability` are accepted.
- Compare with `is()`, never with `===`: two abilities with the same name are two objects.
- A callback that does not need the ability leaves the parameter out: `fn (User $user) => $user->is_editor`.

The policy method `viewAny` maps to `view`, the other standard methods to themselves, and any other method to `Ability::of($method)`. See [Policies](/essentials/policies#abilities).

A perimeter can read the clients' posts and update only its own:

```php
ClientPerimeter::new()
    ->allowed(fn (User $user, Ability $ability) => $user->can("{$ability} client posts"))
    ->should(fn (User $user, Post $post, Ability $ability) => $ability->is('view')
        ? $post->client_id === $user->client_id
        : $post->client_id === $user->client_id && $post->author_id === $user->id)
    ->query(function (Builder $query, User $user, Ability $ability): void {
        $query->where('client_id', $user->client_id);

        if (! $ability->is('view')) {
            $query->where('author_id', $user->id);
        }
    });
```

## Readers of another type

The user that a callback receives is the **reader**: any Eloquent model, such as a `User` or an API client. A perimeter whose callbacks type the reader, such as `fn (User $user, ...)`, applies only to the readers of that type. For another reader, the policy and the queries skip the perimeter, instead of failing with a `TypeError`:

```php
->query(fn (Builder $query, User $user) => $query->where('client_id', $user->client_id))
```

An untyped parameter, `Model`, `object` or `mixed` accepts every reader. Type every callback of a perimeter with the same reader type. See [Readers](/essentials/readers#readers-of-several-types).

## Unrestricted perimeters

A perimeter that reaches every row, such as an administrator's, is declared with `unrestricted()`:

```php
GlobalPerimeter::new()
    ->allowed(fn (User $user, Ability $ability) => $user->can("{$ability} all posts"))
    ->unrestricted();
```

- It takes only `allowed()`. Declaring `query()`, `should()` or search keys with it throws `UnrestrictedPerimeterCallbackException`.
- When it applies to the reader, the controlled queries get no perimeter constraint, the policy grants the row without any `should()`, and no other perimeter narrows it.
- The [boundary](/essentials/boundaries) of the control still applies.

Never write a perimeter for every row as a `query()` that adds nothing: it throws `EmptyQueryCallbackException`.

## Perimeter classes

A perimeter is an instance of a class that extends `Lomkit\Access\Perimeters\Perimeter`. Generate one:

```bash
php artisan make:perimeter ClientPerimeter
```

The class lands in `app/Access/Perimeters`, empty: its rules are the callbacks declared in the control, as above. The class names the rule, in `access:check` and in the errors.

### Rules in the class

A rule shared by several controls can live in the class instead, in three protected hooks:

```bash
php artisan make:perimeter EditorialPerimeter --hooks
```

```php [app/Access/Perimeters/EditorialPerimeter.php]
namespace App\Access\Perimeters;

use App\Models\User;
use Illuminate\Database\Eloquent\Builder;
use Illuminate\Database\Eloquent\Model;
use Lomkit\Access\AccessContext;
use Lomkit\Access\Perimeters\Perimeter;

class EditorialPerimeter extends Perimeter
{
    protected function allows(AccessContext $context): bool
    {
        $reader = $context->reader();

        return $reader instanceof User && $reader->can("{$context->ability()} editorial posts");
    }

    protected function includes(Model $row, AccessContext $context): bool
    {
        $reader = $context->reader();

        return $reader instanceof User && $row->client_id === $reader->client_id;
    }

    protected function scope(Builder $query, AccessContext $context): void
    {
        $reader = $context->reader();

        $query->where('client_id', $reader instanceof User ? $reader->client_id : 0);
    }
}
```

| Hook | Callback it replaces |
| --- | --- |
| `allows(AccessContext $context): bool` | `allowed()` |
| `includes(Model $row, AccessContext $context): bool` | `should()` |
| `scope(Builder $query, AccessContext $context): void` | `query()` |

- Each hook receives an `AccessContext`: `reader()` gives the reader, typed `Model`, so check its class with `instanceof`; `ability()` gives the ability.
- `--hooks` generates the three hooks, which refuse everything until you write them. Remove `includes()` to check the rows in SQL.
- A rule is written once: declaring in the control the callback of a hook that the class overrides throws `OverriddenPerimeterHookException`.
- The control then lists the class with `EditorialPerimeter::new()`, and may still add `allowed()` when the class does not override `allows()`.

### Variants of a class

A class that needs a value for each use, such as the kind of document, keeps it as private state that every hook reads. A required value goes in a constructor with `readonly` promoted properties, behind a named static constructor:

```php
final class OwnedDocuments extends Perimeter
{
    private function __construct(private readonly string $kind) {}

    public static function ofKind(string $kind): self
    {
        return new self($kind);
    }

    protected function includes(Model $row, AccessContext $context): bool
    {
        return $row->kind === $this->kind && $row->owner_id === $context->reader()->getKey();
    }

    protected function scope(Builder $query, AccessContext $context): void
    {
        $query->where('kind', $this->kind)->where('owner_id', $context->reader()->getKey());
    }
}

OwnedDocuments::ofKind('invoice')->allowed(fn (User $user, Ability $ability) => $user->can("{$ability} own invoices"));
```

- Call the named constructor first: the fluent methods clone the perimeter and keep its state.
- `X::new()` on a class whose constructor requires arguments, or is not public, throws `UnbuildablePerimeterException`.
- Build the state from constants, never from the request or the user: the control keeps its perimeters for the whole process. See [Controls](/essentials/controls#pure-perimeter-lists).
- Never narrow a class with a second `query()`, or by wrapping it in another perimeter: the package reads only what each perimeter of the list declares.

## Perimeters are immutable

`allowed()`, `should()`, `query()`, `searchKeys()` and `unrestricted()` return a new perimeter and leave the one they are called on unchanged. Chain the declarations, or keep the returned perimeter:

```php
// Lost: the perimeter in $own has no callback
$own = OwnPerimeter::new();
$own->allowed(fn (User $user, Ability $ability) => $user->can("{$ability} own posts"));

// Kept
$own = OwnPerimeter::new()
    ->allowed(fn (User $user, Ability $ability) => $user->can("{$ability} own posts"));
```

Each callback is declared once: a second `allowed()`, `should()`, `query()` or `searchKeys()` on one perimeter throws `DuplicatePerimeterCallbackException`. Write one callback that checks both conditions.

## Search keys

A perimeter of a searchable model also declares how it is searched, with `searchKeys()`, at the end of its chain. The Search section covers it.
