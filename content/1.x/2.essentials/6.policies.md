## Automatic policies

Call `Access::registerPolicies()` in the `boot()` method of a service provider:

```php [app/Providers/AppServiceProvider.php]
use Lomkit\Access\Access;

public function boot(): void
{
    Access::registerPolicies();
}
```

Every controlled model that has no policy then gets a `Lomkit\Access\Policies\ControlledPolicy` for its control. `can()`, `@can`, `authorize()`, `Gate::allows()` and `Gate::inspect()` work as usual:

```php
$user->can('view', $post);
$this->authorize('update', $post);
Gate::inspect('delete', $post)->code(); // null when granted, or a refusal code
```

A model keeps its own policy when it has one: registered with `Gate::policy()`, declared with `#[UsePolicy]` on the model or a parent class, or found by Laravel's naming convention. The policies are resolved when the Gate asks for them, through `Gate::guessPolicyNamesUsing()`: if your application sets its own guesser, set it before `Access::registerPolicies()`.

## How a decision runs

The policy maps each method to an ability, and asks the control:

| Policy method | Ability | Row |
| --- | --- | --- |
| `viewAny` | `view` | none |
| `view`, `update`, `delete`, `restore`, `forceDelete` | the same | the stored row |
| `create` | `create` | none, or a [draft](#drafts) |
| any other method, through `decideByControl()` | `Ability::of($method)` | a row, a draft or none |

- **Without a row**, such as `viewAny` or `create` without a draft, the ability is granted as soon as the reader reaches one perimeter: an `allowed()` returns `true`. It means "somewhere".
- **With a row**, the row must also be inside the [boundary](/essentials/boundaries) and inside one of the perimeters that allow the reader.

The row is checked in memory by the perimeters that have a `should()` callback or an `includes()` hook, and by an unrestricted one. The other perimeters check it in SQL: one query on the row's key, constrained by the OR of their `query()`. The in-memory checks run first, and the SQL only when none of them grants, so the number of queries never depends on loaded relations.

## Refusals

Each method returns an `Illuminate\Auth\Access\Response`. A refusal carries a code and a translated message, checked in this order:

| Code | Refusal | Status |
| --- | --- | --- |
| `unsaved` | The model is not saved, for any ability but `create` with a draft | 403 |
| `no_perimeter` | No perimeter allows the reader for this ability | 403 |
| `outside_boundary` | The row is outside the boundary for this ability, but the reader may still view it, such as an archived row | 403 |
| `not_found` | The row is outside the boundary for this ability and for `view`, such as a row of another tenant | 404 |
| `outside_rows` | No perimeter that allows the reader contains the row | 403 |

```php
$response = Gate::inspect('update', $post);

$response->allowed();  // false
$response->code();     // 'outside_rows'
$response->message();  // 'You are not allowed to perform this action on this record.'
```

The messages ship in English and French. Publish them to translate or change them, then edit `lang/vendor/access-control/{locale}/refusals.php`:

```bash
php artisan vendor:publish --tag=access-control-lang
```

## Drafts

`create` without a row means "allowed to create somewhere": only the `allowed()` callbacks run. To check **where** the new row lands, pass the model about to be created, the draft:

```php
$draft = new Post($request->validated());

$this->authorize('create', [Post::class, $draft]);

$draft->save();
```

The draft must land inside the boundary and inside one of the reader's perimeters. A user who may only create their own posts cannot create one for another author or another client, whatever the validation lets through.

A draft is not in the database, so only the in-memory checks judge it:

- the `should()` callback or the `includes()` hook of a perimeter, an unrestricted perimeter, and a [`ThroughParent`](/essentials/parents#drafts) that delegates `create`;
- the in-memory form of the boundary: `Boundary::where()`, or the `includes()` hook of a boundary class.

A perimeter checked in SQL cannot grant a draft, and a boundary without an in-memory form refuses every draft. Give a `should()` callback to the perimeters through which users create rows. `php artisan access:check` notes the controls that can grant no draft.

laravel-rest-api always passes the draft: it checks `create` on the class, then on the draft of each row it creates.

## Decisions on the stored row

The policy decides a saved row on the values it has in the database. After `fill()`, `should()` and the boundary receive a copy built from the original attributes:

```php
$post->fill(['author_id' => $user->id]);

$user->can('update', $post); // decided on the stored author, not the new one
```

Check new values through a draft, never by authorizing the modified row.

A model that is not saved is refused with `unsaved` for `view`, `update`, `delete`, `restore`, `forceDelete` and every business ability: decide `viewAny` and `create` without a row, or with a draft.

## Business abilities

A policy declares a business ability, such as `approve` or `export`, by calling the protected `decideByControl()` helper with the name of its method. Extend `ControlledPolicy` and name the control:

```php [app/Policies/PostPolicy.php]
namespace App\Policies;

use App\Access\Controls\PostControl;
use App\Models\Post;
use App\Models\User;
use Illuminate\Auth\Access\Response;
use Lomkit\Access\Decisions\Draft;
use Lomkit\Access\Policies\ControlledPolicy;

class PostPolicy extends ControlledPolicy
{
    protected string $control = PostControl::class;

    public function approve(User $user, Post $post): Response
    {
        return $this->decideByControl(__FUNCTION__, $user, $post);
    }

    public function export(User $user): Response
    {
        return $this->decideByControl(__FUNCTION__, $user);
    }

    public function duplicate(User $user, Post $post, Post $copy): Response
    {
        return $this->decideByControl(__FUNCTION__, $user, Draft::of($copy));
    }
}
```

The perimeters receive `Ability::of('approve')`, so a permission such as `"{$ability} client posts"` reads `approve client posts`. Laravel finds `PostPolicy` by its naming convention, and it replaces the automatic policy for `Post`.

- `$control` names the control of the model. Without it, a row is decided by the control of its model, but `viewAny`, `create` without a draft and a business ability without a row throw `MissingPolicyControlException`. A `$control` that is not the control of the model throws `PolicyControlMismatchException`.
- A business ability on a row about to be created takes `Draft::of($row)`, like `duplicate` above, and is judged in memory like a `create` draft. Passing the unsaved model itself is refused with `unsaved`.
- The standard methods of `ControlledPolicy` stay as they are. `decideByControl` and `declaredControl` are the only names that a policy cannot use for an ability.

### Abilities

The control maps a policy method to an ability with `abilityFor()`. Override it on the control to change the mapping:

```php
use Lomkit\Access\Ability;

public function abilityFor(string $policyMethod): Ability
{
    return match ($policyMethod) {
        'viewAny' => Ability::of('list'),
        default => parent::abilityFor($policyMethod),
    };
}
```

The controlled queries use the same mapping: `controlled('viewAny')` lists the `list` rows here.

## Keep the rules in the control

An overridden method keeps the parameters of `ControlledPolicy`, typed `Model`, and returns a `Response`:

```php
use Illuminate\Database\Eloquent\Model;

public function update(Model $user, Model $post): Response
{
    if ($post->locked_at !== null) {
        return Response::deny('This post is locked.');
    }

    return parent::update($user, $post);
}
```

It works, but the rule lives in the policy only: `controlled('update')` still lists the locked posts, and a [`ThroughParent`](/essentials/parents#the-parents-control-not-its-policy) child does not inherit it. Prefer the control, here a boundary with `readOnlyWhenNotNull('locked_at')`, which keeps a locked post readable and refuses it every other ability: the policy, the lists and the search then agree, which `assertControlAgrees()` checks.

A `Gate::before()` callback that returns `true` grants before the policy runs, whatever the control says.
